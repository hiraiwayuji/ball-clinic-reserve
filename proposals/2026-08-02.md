# V-ARC 週次改善提案｜2026-08-02

---

## 今週の要約（3行）

- キャンセル待ちの自動LINE繰り上げ・初診後フォローLINEシナリオなど「患者定着に直結する自動化」が、競合SaaSでは標準搭載済みなのに対してV-ARCでは未着手のまま。手動対応の限界で機会損失が毎日発生している。
- スタッフ管理では「担当患者のリテンション率を可視化する指標」の追加と「月次1on1チェックイン機能」が、モチベーション維持と定着率向上に高効果と判明。現状のリーダーボードは「作業量」しか測れていない。
- 受付カウンターで「来院サイクルのズレ」をリアルタイムに示すナッジ表示を追加するだけで、スタッフが自然に次回予約の声かけができるようになる。コード改修量は最小・インパクトは最大級の施策。

---

## 提案 1｜キャンセル発生 → ウェイトリスト患者へ自動LINE繰り上げ通知

**観点:** ① 利用者（受付）が使いやすくなる

### 背景・きっかけ

クリニック・サロン向け予約システムの設計ガイド（ripla note記事、医療予約システムの比較サイト等）で「キャンセル待ち自動繰り上げ」が 2025〜2026 年の必須要件として挙がっている。業界ベストプラクティスは「通知 → 30分タイムアウト → 次の人へ」という高速フロー。
現状 V-ARC にはウェイトリスト管理画面（`/admin/waitlist`）があるが、「枠が空いたとき」に何も自動では起きない。受付スタッフが手動でウェイトリストを見て電話する構造になっており、キャンセルが出た夜間や昼食休憩中は完全に機会損失になっている。

参照: https://note.com/ripla_business/n/n1ed2fec5d16d（キャンセル待ち自動繰り上げ設計ガイド）/ https://products.medicalpass.jp/column/reserve02/（クリニックLINE予約の集患活用）

### 提案内容

予約ステータスが `cancelled` または `no_show` に変わった瞬間、そのスロットに対応する `waiting` 状態のウェイトリスト先頭患者に自動でLINEプッシュを送信する。

送信メッセージ例：
```
【ボール接骨院】
8月5日(水) 14:00 の枠が空きました！
ご希望の場合は、このメッセージに「希望」と返信してください（30分以内）。
超過した場合は次の方へご連絡します。
```

- 30分以内に返信があれば自動で予約確定し、受付スタッフにToastで通知
- 返信なし → 次順位の患者へ同じフローを繰り返す
- LINEを登録していない患者の場合は電話番号を受付画面に大きく表示して手動対応を促す

**受付・院長がどう楽になるか:**  
夜間や休憩中でもキャンセル枠が自動で埋まる。受付スタッフがウェイトリストを定期的に確認して電話する手間がゼロになる。

### 期待できる効果

- キャンセルによる機会損失の大幅削減（特に繁忙時間帯）
- 受付業務の手動チェック工数を削減
- 患者満足度向上（「空きが出たらすぐ教えてくれる院」として口コミになる）

### 実装イメージ

- `src/app/actions/adminReserve.ts` — 予約ステータス更新処理（`updateCheckinStatus` 周辺）にウェイトリスト検索 + `pushLineText` 呼び出しを追加
- `src/app/admin/waitlist/page.tsx` — LINE未登録患者へのフォールバック表示を追加
- `src/lib/admin-notify.ts` — 既存 `pushLineText` をそのまま流用可能
- 難易度：**中**（ステータス変更フックの追加 + タイムアウト管理が新規要件）

### 優先度：**高**

患者が来ない枠 = 収益ゼロ。キャンセル発生頻度を考えると、年間の機会損失額は相当大きい。かつ技術的な下地（waitlist テーブル、LINE push 基盤）がすでに整っているため着手コストが低い。

## 提案 2｜受付カウンター「来院サイクルナッジ」バナー表示

**観点:** ① 利用者（受付スタッフ）が使いやすくなる / ② データ分析・経営判断

### 背景・きっかけ

らいらいリザーブ・BeSALO など接骨院・美容サロン系 SaaS では「スタッフが患者対応時にその患者の来院サイクルを即座に確認できるUI」を標準搭載している。  
V-ARC は受付カウンターで `last_visit_days`（前回来院からの経過日数）を計算済みだが、現状は「30日以上空いたらlong_absence扱いにする」チェックリストのトリガーとしてのみ使われている。患者の **平均来院間隔** との比較は行われておらず、スタッフは「何日ぶりか」しか分からない状態。

参照: https://rehasaku.net/media/reservation/3391/（接骨院推奨システム比較）/ https://tol-app.jp/columns/6558（整体院の平均リピート率と来院サイクル）

### 提案内容

受付カウンターの各患者カードに「来院サイクルナッジバナー」を追加。

表示仕様：
- **前回来院日数 vs 平均来院間隔** を並べて表示
- カラーコードで状況を分類：
  - 🟢 緑：平均サイクル内（前回から平均±3日以内）→「順調です」
  - 🟡 黄：平均より5〜14日オーバー → 「次回予約の声かけをどうぞ」
  - 🔴 赤：平均より15日以上オーバー → 「久しぶりです！丁寧なフォローを」

表示例（カード内）:
```
前回から 15日 | 平均サイクル 8日
⚠️ 次回予約の声かけタイミングです
```

**受付・院長がどう楽になるか:**  
スタッフが患者ファイルを開かなくても「この患者はそろそろ来院促進が必要か」を一目で判断できる。声かけのタイミングをシステムが教えてくれるため、スタッフの経験値に依存しなくなる。

### 期待できる効果

- 次回予約率の向上（声かけ漏れを構造的になくす）
- 新人スタッフでも熟練者と同等の患者ケアが可能になる
- データドリブンな患者関係管理の第一歩

### 実装イメージ

- `src/app/actions/adminReserve.ts` — 既存の `last_visit_days` 計算に加え、患者の過去来院履歴から平均来院間隔（`avg_interval_days`）を同時に算出してレスポンスに含める
- `src/app/actions/patientSearch.ts` — 平均来院間隔のロジックがすでに存在（line 224〜246）。このロジックをアドミンの予約取得に流用
- `src/app/admin/counter/page.tsx` — Appointment 型に `avg_interval_days` フィールドを追加し、バナー表示コンポーネントを追加
- 難易度：**小**（ロジックの大半が既存コードに存在、表示追加のみ）

### 優先度：**高**

改修量が少ないにも関わらず、日々の診療で全患者に効果が出る。既存ロジックの活用なので実装ミスリスクも低い。

## 提案 3｜初診後フォローアップLINEシナリオ（3日後・7日後自動配信）

**観点:** ① 利用者（院長・受付）が使いやすくなる / ② データ分析

### 背景・きっかけ

整骨院・接骨院のLINE活用事例を複数調査したところ、「初診後3日以内の自動フォローメッセージが再来率に最も大きく影響する」という知見が共通して出ている。LFLOWの接骨院LINE追客レポートによれば、初診患者へのシナリオ配信（3日後・7日後・14日後）を導入した院では月次の再来院率が 20〜30% 改善した事例がある。  
現在 V-ARC の LINE・販促機能は「手動でターゲットを選んでキャンペーンを送る」方式。`is_first_visit` フラグは予約データに既存だが、初診完了後に自動でフォローする仕組みはない。

参照: https://lflow.net/column/line-sekkotsuin-marketing/（接骨院LINE活用法）/ https://linestep.jp/2025/11/08/chiropractic_line_booking_system/（整体院LINE予約活用術）

### 提案内容

`/admin/marketing` 画面に「初診フォローシナリオ設定」タブを追加。

設定項目：
1. **3日後メッセージ**（テンプレート編集可）  
   例: `ご来院ありがとうございました。その後、お体の具合はいかがでしょうか？気になる点があればいつでもご連絡ください。次回ご来院の際はお気軽にお声がけください😊`
2. **7日後メッセージ**（テンプレート編集可）  
   例: `先日はご来院いただきありがとうございました。1週間が経ちましたが、症状の改善はみられていますでしょうか？定期的なケアをご希望の方は、ぜひ次回のご予約もお待ちしております。`
3. **有効/無効スイッチ**（シナリオ全体のON/OFF）

動作フロー：
- 患者の予約が `completed`（来院完了）になり、かつ `is_first_visit = true` の場合にシナリオキューに積む
- API Route または Supabase Edge Function を使い、毎朝8時に「3日前・7日前に初診完了した患者」を取得してLINEプッシュ送信

**受付・院長がどう楽になるか:**  
初診患者への個別フォロー電話/LINE が院長の業務負荷になっていたが、これが完全自動化される。設定は一度だけ。

### 期待できる効果

- 初診患者のリピート率向上（業界知見では初診後7日以内の接触で継続率が大幅UP）
- 院長・スタッフのフォロー工数をゼロに
- LINE友達リストの活性化（開封率向上）

### 実装イメージ

- `src/app/actions/line-marketing.ts` — フォローシナリオ設定の保存・取得 action
- `src/app/admin/marketing/page.tsx` — 新タブ追加
- 新規: `src/app/api/cron/first-visit-followup/route.ts` — Vercel Cron Job（毎朝8時実行）で初診完了後 3日/7日 の患者を取得し LINE 送信
- Supabase テーブル: `first_visit_followup_queue`（patient_id, scheduled_at, day_offset, status）を新設
- 難易度：**大**（Cron Job 新規設計 + テーブル追加 + メッセージキュー管理）

### 優先度：**高**

患者の最も離脱しやすいタイミング（初診直後）に自動で手を打てる。開院直後から導入すれば複利的に効いてくる施策。難易度は大きいが、投資対効果が最も高い提案の一つ。

## 提案 4｜スタッフ担当「患者リテンション率」ランキングタブ

**観点:** ② データ分析・経営判断がしやすくなる / ③ スタッフ管理・モチベーション向上

### 背景・きっかけ

Square Appointments・BeSALO・ホットペッパービューティー等の美容サロン系 SaaS では、**スタッフ別の顧客リピート率**を標準の分析KPIとして提供している（参照: beauty-pos.jp, squareup.com/us/en/appointments/features）。  
V-ARC の現状リーダーボードは「予約作成数・売上記帳数・経費登録数」という**アクション量**を競うポイント制。これは「患者を連れてくる力」は測れるが、「患者に来続けてもらう力（施術品質・信頼関係構築）」は一切可視化できていない。

参照: https://squareup.com/us/en/appointments/features（Square Appointments の分析機能）/ https://beauty-pos.jp/knowledge-reason/salon-reservation-system/（サロン予約システムのスタッフ別分析事例）

### 提案内容

`/admin/leaderboard` ページに「リテンションランキング」タブを追加。

集計ロジック：
- 各スタッフが担当した初診患者（`is_first_visit=true`）のうち、**30日以内に同じスタッフ担当で再来院した割合** を算出
- 対象期間: 過去3ヶ月（設定で変更可）

表示例：
```
リテンションランキング（過去3ヶ月）

🥇 田中スタッフ  初診担当38人 → 30日リピート 76% (29人)
🥈 佐藤スタッフ  初診担当25人 → 30日リピート 68% (17人)
🥉 鈴木スタッフ  初診担当19人 → 30日リピート 58% (11人)
```

- 現行の「ポイントランキング」タブと切り替え表示
- 件数が少ないスタッフは `n<5で表示なし` などの最低サンプル数フィルター

**受付・院長がどう楽になるか:**  
「どのスタッフが患者に来続けてもらえているか」が月次で把握でき、院長が評価・育成に使えるエビデンスになる。スタッフ自身は「リピートしてもらう施術」を意識するようになる。

### 期待できる効果

- 施術品質の自然な向上（数字で自分の実力が分かる）
- 院長の評価根拠がデータベースになり、昇給・役割分担の説得力が増す
- 患者-スタッフのマッチング施策（リテンション率の低いスタッフを補佐するシフト配置など）に活用可能

### 実装イメージ

- `src/app/admin/leaderboard/page.tsx` — タブ追加（`"points" | "retention"` の切り替え）
- `src/app/actions/security.ts` — `getStaffRetentionRanking()` 関数を新規追加（appointments テーブルを staff_id × is_first_visit × 30日以内再来院でグループ集計）
- Supabase クエリ: `appointments` テーブルへのウィンドウ関数 or サブクエリ
- 難易度：**中**（SQL クエリ設計が核心、UI は既存リーダーボードを踏襲）

### 優先度：**中**

既存リーダーボードの延長として追加できる。施策の効果は「データを見た院長がどう動くか」に依存するため、実装後に使われる文化を作る必要がある。先にポイント制が定着してから追加するのが自然。

## 提案 5｜月次スタッフ1on1チェックイン機能（院長 ↔ スタッフ）

**観点:** ③ スタッフ管理がしやすく、スタッフのモチベーションが上がる

### 背景・きっかけ

人事評価SaaS「O:」が 2025 年に1on1向け機能を大幅強化したニュース（DXマガジン記事）によると、**月次チェックイン**（体調・メンタル・目標進捗の定期確認）を導入した組織ではスタッフ定着率が向上し、院長-スタッフ間の信頼関係が可視化されるという。また aspicjapan.org の1on1ツール比較記事では「記録の蓄積」が最も重要な機能要件として挙げられている。  
接骨院でスタッフ離職率が高い最大の原因は「自分がちゃんと評価されているか分からない」という不安感。現状の V-ARC にはスタッフ向けの自己申告・フィードバック機能が一切ない。

参照: https://dxmagazine.jp/DX最新ニュース/新製品・サービス/0vw2p（O:の1on1機能強化）/ https://www.aspicjapan.org/asu/article/9775（1on1ツール比較15選）/ https://jinji-dx-sainavi.com/categories/motivation-management/（モチベーション管理システム86選）

### 提案内容

`/admin/settings/staff-schedule` の設定画面に「月次チェックイン」タブを追加。

**スタッフ側（月末に入力）:**
1. 今月うまくいったこと（自由記述）
2. 今月難しかったこと・課題（自由記述）
3. 目標達成度（1〜5のスライダー）
4. 院長に相談したいこと（自由記述 or 「なし」）
5. 来月チャレンジしたいこと（自由記述）

**院長側（スタッフ提出後に確認）:**
- 全スタッフの回答を一覧で確認（テーブル表示）
- 各回答に「院長コメント」を1行で返信できる
- 前月・前々月の回答も履歴として参照可能

**通知フロー:**
- 毎月25日に「月次チェックインを提出してください」をシフトリマインダーと同様にLINEで各スタッフへ自動通知
- 院長には未提出スタッフ数をダッシュボードカードで表示

**受付・院長がどう楽になるか:**  
院長が全スタッフの状態を月に1回まとめて把握できる。面談の時間が取れなくても、テキストで現状把握→コメント返信という非同期コミュニケーションが成立する。スタッフは「自分の声を届ける場所がある」という安心感を得る。

### 期待できる効果

- スタッフ離職防止（「評価されている実感」が最大の定着要因）
- 院長の1on1準備時間の削減（チェックインシートが事前アジェンダになる）
- 半期・年次評価の根拠データとしてアーカイブ活用可能
- 問題の早期発見（「難しかったこと」欄でスタッフの困りごとが可視化）

### 実装イメージ

- 新規テーブル: `staff_monthly_checkins`（`id, clinic_id, staff_user_id, month, answers_json, manager_comment, submitted_at`）
- `src/app/actions/staff-schedule.ts` — `submitMonthlyCheckin()` / `getMonthlyCheckins()` / `saveManagerComment()` を追加
- `src/app/admin/settings/staff-schedule/tabs/` — `CheckinTab.tsx` を新規作成
- `src/app/admin/dashboard/DashboardClient.tsx` — 未提出スタッフ数バッジを表示するカードを追加
- 既存のシフトリマインダー基盤（`shift-reminders.ts`）を流用して月次通知を実装
- 難易度：**中**（テーブル設計はシンプル、UI は既存タブパターンを踏襲）

### 優先度：**中**

スタッフが複数院にまたがって多人数になるほど効果が大きくなる。すぐに実装しなくても今のうちから設計を固めておくと、3院・4院体制になったときに一気に差が出る機能。
